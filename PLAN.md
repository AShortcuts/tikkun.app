### What we're doing

Replace the three competing search implementations in the Reader Command Palette, Reader Parsha Picker, and public Readings & coverage page with one typed, local search system. It will combine deterministic parsing for pages, aliyot, and Torah references with Fuse.js token retrieval for spelling variants and typos, then apply app-owned ranking, deduplication, scope, and context rules. The migration will preserve existing routes, filters, keyboard behavior, lazy loading, offline operation, and real project data while making search safe and consistent.

### Steps

1. [x] Capture the baseline and define relevance before changing behavior: record current bundle/chunk sizes and search lifecycle, then add a table-driven “golden query” corpus covering exact English and Hebrew names, nikkud, maqaf/apostrophe variants, known transliterations, abbreviations, one-character typos, `Noach 3`, `Maftir`, page and book/chapter/verse forms, empty queries, duplicates, filters, and hostile input such as `[`. Assert stable result IDs and Top-1/Top-3 expectations rather than library scores.
2. [x] Add the current compatible full `fuse.js` runtime dependency and build a browser/SSR-safe search foundation under `app/search/`: typed documents and matches, Unicode normalization with original-character index mapping, conservative tokenization, a structured query parser, and one index wrapper. Retrieval will favor recall; deterministic ranking bands will enforce parsed intent, exact primary name, exact alias, all-token prefix, all-token fuzzy, then partial fallback, with fuzzy matching disabled for short tokens, stable tie-breaking, deduplication before limits, and context boosts unable to cross relevance bands.
3. [x] Define focused adapters instead of one oversized global catalog: reading documents will reuse canonical parsha-route aliases and holiday keywords; action documents will distinguish primary labels, aliases, discovery keywords, availability, destination identity, and explicit empty-state priority; public coverage documents will use `PublicReading` data and status filters. Keep Fuse in feature-specific modules so `/readings/`, the lazy Parsha Picker, and the lazy Command Palette load it only when needed, while homepage imports of `src/lib/readings.ts` remain lightweight.
4. [x] Migrate the public Readings & coverage search first behind a page-only `reading-coverage-search` adapter. Preserve status filtering and original catalog order for an empty query; rank matching readings for a non-empty query; support Hebrew/English aliases and typo tolerance; retain the honest empty state, result count, real coverage data, and current links. Add model and route tests proving filters compose with search and that the homepage bundle does not inherit the search dependency.
5. [x] Migrate the Parsha Picker by constructing its index once per model/mount and replacing `fuzzy()` behind the existing `model.search()` seam. Preserve the five-result limit, keyboard navigation, focus, and Hebrew/English highlighting; expose matched-alias context when the displayed title was not the matching field; safely resolve structured aliyah/reference queries to canonical existing routes; and test double portions, holiday services, empty/no-result behavior, special characters, teardown, and calendar-setting rebuilds.
6. [x] Migrate the Command Palette to a persistent action index created on open and rebuilt only by its existing `refresh()` lifecycle. Replace insertion-order suggestions with explicit empty-state priorities, keep unavailable actions excluded, preserve the twelve-result limit and runnable callbacks outside indexed documents, add match metadata without cluttering the UI, and verify pages, tools, current reading, future readings, recordings, bookmarks, resume points, holidays, aliases, deduplication, keyboard selection, focus restoration, dynamic refresh, lazy-load retry, and cleanup.
7. [x] Remove the legacy regex-based `app/fuzzy.ts` and fixed command scorer only after every consumer and test has moved; update architecture documentation; run focused unit/browser tests, the full test suites, typecheck/lint, production build, and service-worker checks. Compare final chunk sizes and index/search timings with the baseline, confirm no index rebuild occurs per keystroke, and keep the new shared search chunks precached while media and deferred optional features retain their existing cache policy.

### What we're NOT doing

- No semantic or AI search for concepts inside Torah text, commentary, or audio.
- No hosted search service, server dependency, tracking, personalized ranking, or query-history storage.
- No redesign of the three search interfaces, result limits, coverage filters, Reader routing, or calendar rules.
- No automatic transliteration guesser; supported alternate spellings remain explicit, reviewable aliases.
- No changes to isolated prototypes, generated manifests, media download behavior, or unrelated dirty-worktree files.

### How we'll know it works

1. The golden query suite returns the intended canonical result first across all applicable surfaces, handles typos and Hebrew variants, never crashes on arbitrary input, and produces no duplicate destinations.
2. Browser tests prove keyboard/focus/highlighting, direct navigation, filters, dynamic palette refresh, lazy loading, cleanup, and one-time index construction continue to work with real catalog data.
3. `npm test`, `npm run test:browser`, `npm run check`, and `npm run build` pass; the built app remains static and offline-capable, and measured search/bundle costs stay within the recorded baseline budget.
